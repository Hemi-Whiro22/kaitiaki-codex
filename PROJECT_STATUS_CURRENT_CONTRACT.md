# Project Status

Purpose of rewrite:
- Preserve the project state summary without locking it to outdated phase claims or one old implementation stack.
- Turn the document into a durable status-and-direction note.

Source document:
- `PROJECT_STATUS.md`

Rewrite posture:
- local-first
- anti-drift
- no invention

## System Direction

The project direction remains:
- local-first by default
- guardian-centered
- lane-aware by `pou`
- staging before endpoint truth
- portable across implementation profiles

## What Exists In Principle

The system already has a coherent conceptual shape:

- an interaction surface
- a guardian layer
- backend service lanes
- shared staging
- endpoint storage by lane
- relational memory
- indexing and semantic retrieval support
- governance and ownership documentation

## What Must Remain True

The following are architectural requirements, not optional preferences:

- the guardian validates and routes
- the guardian does not become a reasoning engine
- `pou` boundaries remain explicit
- `tapu_level` remains a real handling boundary
- staging is not mistaken for trusted endpoint truth
- the interaction edge remains replaceable

## Current Priorities

### Structural Clarity
- keep documents aligned to system roles
- prevent framework or provider lock-in in core docs

### Trusted Intake
- maintain shared staging
- require guardian clearance before endpoint promotion

### Memory And Relational Recall
- preserve `whakapapa` as the relational memory lane
- keep memory tied to handling posture and lane ownership

### Service Separation
- keep translation, research, guardian, intake, and build work in their own lanes

## Near-Term Work

The next useful work should strengthen:
- guardian enforcement
- clear staging-to-endpoint flow
- lane-specific service boundaries
- profile-specific run instructions
- docs as architecture source

## Risks To Watch

- reintroducing a smart “orchestrator” that reasons instead of guarding
- collapsing intake and trusted endpoint data into one store
- treating UI/provider details as core architecture
- letting one service lane impersonate the whole system

## Current Translation

The original document was a detailed project progress snapshot for an older stack and phase model. The durable meaning was:
- what major capabilities existed
- what was still intended
- what direction the platform was moving in

This rewrite keeps that status function, but expresses it as a durable architecture-state summary rather than a dated stack report.

## Status Summary

- Keep:
  - system overview
  - feature/state visibility
  - honest acknowledgment of what is still to be built
- Change:
  - stack-specific completion tables into architecture-state priorities
  - phase claims into ongoing direction
- Drop:
  - dated counts, completion badges, and old service inventories as core truth

## Open Questions

- Which parts of the old phase model are still useful as implementation planning?
- Should there be a separate live status document for the current implementation profile only?

## Historical Memory Still Valuable

- The original desire to make progress legible.
- The emphasis on system-wide visibility rather than hidden changes.

## Not Current Runtime Truth

- old phased completion claims
- old service matrix as the live platform map
- old provider, database, and container assumptions as universal architecture
